Architecture Forum — High Level Design

Metadata-Driven Ingestion Framework

A reusable, configuration-controlled data integration layer on Azure that eliminates per-source pipeline development and centralises all ingestion behaviour in a single metadata control plane.

Version 2.0 August 2026 Classification: Internal
01 — Overview

Executive Summary

The Metadata-Driven Ingestion Framework provides a single, reusable, and centrally governed data integration layer on Azure. Instead of building a dedicated pipeline for each data source, a suite of generic Azure Data Factory pipelines covers all ingestion scenarios — with runtime behaviour driven entirely by metadata stored in a central Azure SQL schema (EDP_Metadata).

Onboarding a new data source requires no pipeline development or deployment. A metadata record is inserted into the control table and the existing generic pipeline automatically handles the ingestion — resolving connections, dataset types, file formats, column delimiters, load strategy, and target paths at runtime from the metadata.

The framework supports both Full Refresh and Incremental (Delta) load patterns, Ingress and Egress activity directions, and a broad range of source and target connectors across file-based and database systems. As of v2.0, four pipelines covering Azure SQL and ADLS Gen2 source/target combinations are fully deployed and operational, with support for standard formats (CSV, Parquet, JSON), compressed sources (GZIP, ZIP, TarGzip), and binary file pass-through.

Configuration-level parameters shared across all pipelines — such as the metadata server and database coordinates — are managed as ADF Global Parameters, removing them entirely from individual pipeline definitions and providing a single configuration point at the factory level.

02 — Context

Problem Statement

Without a metadata-driven approach, data engineering teams typically encounter the following challenges as the number of ingestion requirements grows:

  • Pipeline proliferation — A dedicated pipeline per source/target combination results in hundreds of near-identical, independently maintained artifacts with no shared behaviour.
  • Hardcoded configuration — Connection strings, file paths, table names, and schema references are embedded in pipeline definitions, requiring a full redeployment cycle for any configuration change.
  • No central control — Activating or deactivating a specific ingestion job requires modifying triggers or pipeline definitions rather than updating a flag in a control table.
  • Slow source onboarding — Each new data source demands a full pipeline build, review, test, and deployment cycle — typically days to weeks per source at scale.
  • Inconsistency — Without enforced naming and structural conventions, pipeline implementations diverge across teams and projects, making operational management and tooling difficult.
  • Ad hoc watermark management — Incremental load tracking (high-water marks) is typically implemented per-pipeline, with no centralised state or visibility.
  • Poor auditability — There is no structured record of who configured a given ingestion job, when, or what was changed.

Runtime View — MasterRef

EDP_Metadata.MasterRef is a denormalized view that joins MetadataRef with all its lookup tables. The ADF Lookup activity targets this view to retrieve the complete runtime configuration for a given Trigger_Name in a single query. The view also derives two computed values:

  • Pipeline_Name — Derived from input source reference, output source reference, load type, and activity direction. Format: PL_{InputSource}_{OutputSource}_{FULL|INCREMENTAL}_{INGRESS|EGRESS}
  • SwitchCaseRef — Derived from the input and output linked service names and file formats. Used by the ADF Switch activity to select the correct Copy activity for the connector/format combination.

05 — Execution Model

Runtime Execution Model

At runtime, ADF resolves all parameters from the metadata control plane. No configuration is embedded in the pipeline definition. The execution sequence for any ingestion job is identical regardless of source, target, or load pattern:

  1. A scheduled or event-based trigger fires in Azure Data Factory, passing the TriggerName as a pipeline parameter.
  2. A Lookup activity queries EDP_Metadata.MasterRef with firstRowOnly: false, returning the complete runtime configuration for every active job belonging to that trigger — source and target connections, dataset types, file formats, column delimiters, load type, watermark state, and JSON runtime settings — in a single multi-row result. The Lookup dataset references the metadata Azure SQL database via ADF Global Parameters (@pipeline().globalParameters.MetadataServerName and @pipeline().globalParameters.MetadataDatabaseName).
  3. A ForEach activity iterates over all returned rows in parallel (batch size 5), passing each job's full metadata row to the activities nested within it.
  4. A Switch activity evaluates the SwitchCaseRef value from the current iteration's row to route execution to the correct activity set for the connector and file format combination.
  5. The Copy activity executes using fully dynamic ADF expressions. Container names, directory paths, filenames, SQL queries, schema and table names are all sourced from MetadataSettingsInput and MetadataSettingsOutput JSON at runtime — nothing is hardcoded in the pipeline definition.
  6. For Incremental jobs: the watermark boundary is applied as a source-side filter before the copy. After a successful copy that transfers at least one row (or file), the Watermark_Value is updated to UTC now via a Script activity against the metadata database. If the copy transfers zero rows, the watermark is intentionally not advanced — ensuring the same time window is retried on the next run.

08 — Load Patterns

Load Patterns

The framework supports two load patterns, controlled by the Load_Type flag on MetadataRef. Both patterns flow through the same generic ADF pipeline — the metadata determines the behaviour.

Full Refresh  Load_Type = Full_Refresh

The entire dataset is read from source and written to the target on each run. Used for reference data, small dimension tables, or sources where change tracking is not available or required.

  • Watermark_ID is NULL — no high-water mark is maintained.
  • No source-side filter is applied; all records are copied on every run.
  • Each Switch case contains a single Copy activity. No watermark validation or update activities are needed.
  • Pipeline name carries the FULL suffix.

Incremental / Delta  Load_Type = Incremental

Only records added or changed since the last successful run are copied. The high-water mark is maintained in the Watermark table and updated after each successful load that transfers at least one record. Suited to large transactional datasets where a full reload on each run is not practical.

  • Watermark_ID references a row in the Watermark table.
  • For SQL sources: Watermark_Column identifies the datetime column on the source table. The source query wraps the user-supplied query with WHERE {Watermark_Column} > '{Watermark_Value}'.
  • For file-based sources (ADLS): The modifiedDatetimeStart property in AzureBlobFSReadSettings filters files by last-modified timestamp. Watermark_Column serves as a documentation label only.
  • After a successful copy that transfers data, a Script activity updates Watermark_Value to UTC now in the metadata database.
  • Pipeline name carries the INCREMENTAL suffix.

09 — Failure & Edge Cases

Incremental Pipeline Resilience

The incremental pipelines implement multiple defensive patterns to handle edge cases that would otherwise result in silent data loss, incorrect watermark advancement, or hard-to-diagnose failures. Each guard is implemented as a discrete ADF activity with explicit dependency conditions.

Why these guards matter: Without them, a pipeline could advance the watermark on a failed copy (losing the retry window), silently advance on an empty result (masking a missing data issue), or run indefinitely with a null watermark (copying all records on every run with no filtering). Each scenario below has been considered and explicitly handled.
WM001 Null Watermark Validation Guard

Risk: If Watermark_Column or Watermark_Value is null in the metadata, the incremental source filter cannot be constructed. The copy would proceed unfiltered, loading the entire source on every run — identical to a full refresh but without the watermark update, silently corrupting the incremental state.

Implementation: An IfCondition activity (Validate_Watermark) evaluates:

@or(equals(item().Watermark_Column, null), equals(item().Watermark_Value, null))

If the condition is true (either field is null), a Fail activity fires immediately, halting the pipeline run with error code WM001 and a message identifying the Metadata_Job and Metadata_ID. The Copy activity never executes.

Scope: All 3 ASQL incremental cases  |  Original 9 uncompressed ADLS incremental cases  |  Not applied to 19 compressed/binary ADLS cases (activity limit constraint — see below)
ZR001 Zero-Rows / Zero-Files Guard Guard

Risk: If the watermark-filtered source query returns zero rows (e.g. no new records since the last run, or a temporary data gap), advancing the watermark would shift the time boundary forward — potentially causing the next run to miss records that arrive late but within the original window.

Implementation: An IfCondition activity (Check_Rows_Copied) evaluates the Copy activity's output metric after the copy completes:

/* Standard format cases (CSV, Parquet, JSON): */ @greater(activity('Copy_...').output.rowsCopied, 0) /* Binary case: */ @greater(activity('Copy_ADLS_BINARY_to_ADLS_BINARY').output.filesRead, 0)

The Update_Watermark Script activity is nested in the ifTrue branch only. If zero rows (or zero files) were transferred, the watermark is not advanced and the same time window is retried on the next run.

Scope: All 28 cases in both ADLS incremental and all 3 ASQL incremental cases  |  Binary case uses filesRead; all other cases use rowsCopied
CF001 Copy Failure Guard Guard

Risk: If the Copy activity fails mid-run (network error, schema mismatch, throttling, etc.), a watermark update that runs regardless would lock the pipeline into a future time window — permanently skipping all records from the failed run's interval.

Implementation: The Check_Rows_Copied (IfCondition) activity has an explicit dependency on the Copy activity with condition Succeeded. If the Copy fails, the IfCondition — and therefore the Update_Watermark Script activity — is skipped entirely. The watermark remains at the last known good boundary, ensuring the next retry re-processes the same time window.

/* Dependency condition on Check_Rows_Copied: */ "dependsOn": [{ "activity": "Copy_...", "dependencyConditions": ["Succeeded"] }]
Scope: All 28 cases in both ADLS incremental and all 3 ASQL incremental cases
FW001 ADLS File-Modification Watermark Design

Challenge: File-based sources on ADLS Gen2 have no SQL column that can be used to filter rows by a watermark value. The standard SQL approach (WHERE column > value) cannot be applied to files.

Implementation: ADF's native modifiedDatetimeStart setting in AzureBlobFSReadSettings is used to filter files by their last-modified timestamp. Only files modified on or after the watermark boundary are included in the copy:

"storeSettings": { "type": "AzureBlobFSReadSettings", "modifiedDatetimeStart": { "value": "@formatDateTime(item().Watermark_Value, 'yyyy-MM-ddTHH:mm:ss')", "type": "Expression" } }

Watermark_Column in the metadata row for file-based sources acts as a human-readable documentation label (e.g. FileModifiedDate) and is not used in the ADF filter expression. Only Watermark_Value is consumed at runtime.

Scope: All 28 cases in PL_ADLS_ADLS_INCREMENTAL_INGRESS  |  Not applicable to ASQL incremental (SQL column filter used instead)
BN001 Binary File Metric Substitution Design

Challenge: ADF's Binary Copy activities do not report rowsCopied — binary transfers report filesRead and filesWritten instead. Using the standard rowsCopied metric for the zero-rows guard would always evaluate to zero, causing the watermark to never advance for binary jobs.

Implementation: The binary incremental case uses filesRead in the Check_Files_Read guard condition:

@greater(activity('Copy_ADLS_BINARY_to_ADLS_BINARY').output.filesRead, 0)

The Update_Watermark Script activity is otherwise identical to all other incremental cases — only the guard metric differs.

Scope: Binary-to-binary switch case only (SW_ADLS_SAMI_BINARY_ADLS_SAMI_BINARY) in PL_ADLS_ADLS_INCREMENTAL_INGRESS
AL001 ADF 120-Activity Limit Workaround Constraint

Constraint: Azure Data Factory enforces a hard limit of 120 nested activities per pipeline. All activities at every nesting level — including activities inside IfCondition branches and Switch cases — count toward this total.

Problem: PL_ADLS_ADLS_INCREMENTAL_INGRESS needed 28 Switch cases. Applying the full 5-activity pattern (Validate_Watermark + Fail + Copy + Check + Update) to all 28 cases would yield 143 activities total (28 × 5 + 3 = 143), exceeding the limit.

Solution: The 19 compressed and binary cases use a simplified 3-activity pattern (Copy + Check + Update), omitting the Validate_Watermark guard. The 9 original uncompressed cases retain the full 5-activity pattern:

9 original cases x 5 activities = 45 19 compressed/binary cases x 3 activities = 57 3 outer activities (Lookup + ForEach + Switch) = 3 Total = 105 (within limit)

The risk of omitting Validate_Watermark for the 19 new cases is accepted: metadata configuration quality controls (referential integrity in the Watermark table) should prevent null watermark states from occurring in practice. This constraint is documented here for operational awareness.

Scope: PL_ADLS_ADLS_INCREMENTAL_INGRESS only  |  No constraint on other pipelines (105 / 120 activities used)

Watermark Update — Script Activity

When the zero-rows guard confirms data was transferred, the watermark is advanced using a Script activity connected to LS_ASQL_SAMI (the metadata database linked service). The SQL script updates the Watermark table via a join to MetadataRef using the current iteration's Metadata_ID:

UPDATE w SET w.Watermark_Value = CONVERT(DATETIME, '<utcNow formatted yyyy-MM-dd HH:mm:ss>') FROM EDP_Metadata.Watermark w JOIN EDP_Metadata.MetadataRef m ON m.Watermark_ID = w.Watermark_ID WHERE m.Metadata_ID = <item().Metadata_ID>

The script uses a NonQuery command type and all values — the UTC timestamp and Metadata_ID — are dynamically resolved via ADF expressions. No watermark coordinates are hardcoded in the pipeline definition.

11 — Design

Design Principles

Metadata-Driven Architecture

Pipeline behaviour is fully parameterized. No source path, connection detail, file format, or load type is hardcoded in any ADF pipeline definition. All execution decisions are resolved at runtime from the metadata control plane.

Separation of Configuration from Execution

The metadata layer owns what to do; ADF owns how to do it. Operational and configuration changes require no pipeline modification or redeployment — they are made purely in the metadata.

Single Source of Truth

All ingestion configuration lives in EDP_Metadata.MetadataRef. No configuration is duplicated across pipelines, environments, or teams. The MasterRef view exposes a complete denormalized runtime view over this single source.

Centralised Operational Control

The IsActive flag provides a master on/off switch for any ingestion job without touching ADF triggers or pipeline definitions. Operational state is managed in data, not in infrastructure.

Convention over Configuration

Strict, computed naming conventions for pipelines, datasets, linked services, and switch cases are enforced by the metadata schema. Consistent naming reduces cognitive load and enables automated operational tooling.

Auditability by Design

Every row in MetadataRef carries Created_Date, Modified_Date, and Modified_By — populated automatically by database defaults. Configuration change history is inherent to the data model, not an afterthought.

Defensive Incremental Loading

Incremental pipelines implement multiple explicit guards: null watermark validation, zero-rows checks before advancing the boundary, and Copy Succeeded dependency conditions on watermark updates. Watermarks are never advanced on failure or empty results.

Extensibility

Adding a new data source, file format, or authentication type requires only inserting reference rows into the appropriate lookup tables. The generic pipeline accommodates new source/target combinations without any pipeline modification.

Idempotent Infrastructure

All DDL scripts use IF NOT EXISTS guards and include schema upgrade paths. The schema can be safely re-applied across environments — development, test, production — without destructive side effects.

12 — Governance

Data Fabric Alignment

The framework aligns with several foundational principles of modern Data Fabric architecture, specifically those concerned with active metadata management, unified cataloguing, and governed connectivity.

Data Fabric PrincipleHow the Framework Addresses It
Active Metadata Management MetadataRef is a live operational control plane — not passive documentation. It actively governs pipeline behaviour at execution time, making metadata the direct engine of data movement.
Unified Data Catalogue All sources, target types, file formats, authentication methods, and connection configurations are centrally registered in the EDP_Metadata schema. No shadow configurations exist outside this registry.
Business Domain Orientation BusinessDomainRef classifies every ingestion job by business function. Every data movement activity is traceable to its owning domain — supporting data product thinking and domain-driven data governance.
Governed Connectivity SystemAuth and LinkedServiceRef enforce a structured, centralised approach to connection management. All authentication types and connection templates are catalogued and reused — there are no unregistered or one-off connections.
Reusable Data Services The generic pipeline layer acts as a reusable data service. The same pipeline infrastructure serves all projects, domains, and customers without modification; variation is expressed purely in metadata records.
The framework addresses the ingestion layer of a Data Fabric architecture. It is designed to integrate with broader platform components — data catalogues, lineage tools, and data quality frameworks — that complete the fabric.
